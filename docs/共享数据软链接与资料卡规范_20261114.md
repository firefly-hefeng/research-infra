## 2. 两机观察与已经完成的入口

已使用 rmp 检查 `47.117.138.84` 和 `101.132.97.146`。两机 `/data/share` 的挂载来源均为 `10.0.0.202:/share`，类型 NFS；本次在 101 机器创建后，47 机器也观察到新增链接，验证了共享可见性。

```text
/data/share/
├── dataset -> datasets       新增相对软链接
├── model   -> models         新增相对软链接
├── datasets/                 原目录，保留
├── models/                   原目录，保留
├── public/                   原目录，保留
└── incoming/                 原目录，保留
```

操作结果：

- `/data/share/dataset` 与 `/data/share/datasets` 指向同一目录对象。
- `/data/share/model` 与 `/data/share/models` 指向同一目录对象。
- 两机均已检查链接目标、目标 inode、访问状态。
- 源目录的 inode、mode、uid、gid 在创建过程中保持一致。
- 不删除已存在的其他入口或目录，不重新执行历史迁移脚本。
- NFS 客户端可能短暂缓存“路径不存在”，创建后需在另一台重新核验，不应因第一次查不到而覆盖重建。

**软链接不是副本。** 原路径的数据继续保留，新入口只增加引用，因此不新增一份完整数据占用；它不会释放历史副本的空间，也不提供额外备份。原目标移动、删除或权限变化会影响链接可用性。

## 3. 原路径与跨服务器约束

观察到两机的旧路径并不完全相同：

- 101 机器的 `/data/datasets`、`/data/models` 已是指向共享区的旧链接。
- 47 机器同名路径仍是目录。此次完整保留，不重定向、不合并。
- `/data/users/...` 是个人路径；两机同样的字符串不证明它们是同一份数据，存在性和访问权限也可能不同。

共享盘上的软链接由**访问它的客户端**解析目标路径。如果目标是只存在于其中一台的本地目录，另一台会遇到断链或访问到不同内容。

因此，正式加入共享目录的资源应同时满足：

1. 资源明确允许团队共享，且来源范围已经确认。
2. 目标在所有使用节点上指向同一份可用存储；优先使用已存在的共享盘目标。
3. 目标路径没有循环引用，不以链接进入私有数据边界。
4. 目标名称不存在；存在时只核对并记录，不覆盖。
5. 权限符合预期。软链接不替代目标文件权限，也不扩大许可范围。

本次没有将个人目录中的条目批量链接到公共根下，也没有为了让链接可读而 chmod 或更改所有者。

## 6. 面向研究员与 Agent 的资料卡

每个资源包含同源的 JSON 和 Markdown 两种表示：JSON 供 Agent 消费，Markdown 供人员阅读。

| 字段 | 规则 |
| --- | --- |
| resource_id | 稳定资源标识；本次生成候选 ID，尚未与门户 asset_id 做身份合并 |
| name、kind | 名称与资源类型 |
| category | 主分类、细分类及来源依据 |
| locations | 服务器、原路径、共享入口、链接目标、观察时间与访问状态 |
| scale | 数量、字节数、统计单位、口径与证据；未知保留未知 |
| version | 上游版本、revision 或发布号；没有证据时 unconfirmed |
| usage_conditions_claimed | 来源记载的使用限制；人工审核后再确认共享范围 |
| visibility | 内部、团队共享或公网元数据；分别控制 |
| source | 表格、工作表、行号与文件摘要 |

| unknowns_claimed | 来源记载的待补事项 |

本次所有卡片都是 `internal_review`，`public_metadata: false`。原始个人路径、许可申请材料与受限信息不会因为制作卡片而自动上公网。

规模与版本原则：

- 文件数、录音数、样本数、参与者数分别记录。
- 不把目录占用、压缩包大小和展开大小累加成唯一数据体积。
- 部分取得的资源明确标记 partial，不列为完整可用数据集。
- 保留来源中的旧结论和后续更新差异，不把“已取得”自动转换成“已完成训练”。

## 7. 直接上传规则设计

目标体验：用户可在 `/data/share/datasets` 或 `/data/share/models` 下上传允许团队共享的资源，每个资源使用独立名称和版本。

建议新资源结构（规划，未在服务器新建）：

```text
/data/share/datasets/<resource-slug>/<version>/
├── payload/       原文件
└── README.md      名称、来源、许可、内容、版本、数量口径和上传完成状态
```

模型使用相同结构，另说明框架、配置、权重格式、输入输出、模型版本和适用任务。

规则：

1. 只有具有团队共享依据的数据可以上传到公共入口。个人申请获批或私有采集数据继续放个人路径。
2. 每次使用新的资源名或版本名，禁止覆盖既有资源。
3. 上传过程中标记 uploading；全部传完后更新完成声明，Agent 才进入核验。
4. Agent 至少经过两次稳定观察，并结合完成声明判断可收录，不能只根据目录存在判断上传完成。
5. 不强制重命名用户文件，版本关系通过资料卡记录。
6. 向软链接下写入等于向原目标写入，不存在独立副本隔离。
7. 数据有变更时追加新版本；维护日志记录变化，不在资源正文暴露个人上传日志。

**当前权限尚不支持所有用户直接上传。** 两机的 `/data/share/datasets`、`/data/share/models` 为 root 所有、0755，rmp 对根目录没有写权限。单数入口只是别名，不改变这个事实。

正式启用直接上传，需要单独确定上传组、每人可写子目录或 ACL 策略。这会涉及新建目录／权限配置，超出本次“只能新建软链接”的限制，所以本次没有执行，也没有宣称上传功能已启用。

## 8. Agent 监控与隐藏日志设计

### 8.1 信息分离

- 用户可见：资源目录、资料卡、版本、共享位置、可用状态、更新时间。
- 管理员／Agent 可见：扫描记录、变化差异、异常、写入行为、审核与来源证据。
- 公网 AI 可见：另外审核过的公开说明。团队共享文件路径不等于公网下载地址。

“日志不展示”必须由文件权限和 API 白名单落实，不能仅靠前端隐藏按钮。

### 8.2 日志位置与格式

建议放在服务主机本地专用位置，例如 `/var/lib/research-data-center/catalog-monitor/`，由专用服务账户维护，目录 0700、日志 0600；不要放到 `/data/share/datasets`、`/data/share/models` 或网站静态目录。以上目录及权限仅为设计，未创建。

采用追加式 JSONL：

```json
{
  "event_id": "唯一事件ID",
  "observed_at": "带时区的观察时间",
  "scanner_host": "扫描节点",
  "resource_id": "稳定资源ID",
  "event_type": "resource_discovered",
  "source_path": "管理员可见的内部路径",
  "before": null,
  "after": {"state": "pending_review"},
  "actor": null,
  "actor_basis": "not_observed"
}
```

事件包括发现资源、上传中、说明更新、版本变化、链接失效、权限不可用、收录成功、审核撤回。文件所有者不能当作实际操作者；仅靠轮询无法准确知道是谁修改了文件，也无法发现两次扫描之间短暂出现又消失的变更。

建议后续采用日期分段追加日志，独立管理员备份策略；当前不配置删除或清理任务。

### 8.3 监控流程

1. 只扫描授权根和登记资源入口，限制深度、文件数量与耗时。
2. 读取链接自身及目标信息，识别循环、越界、断链和权限错误。
3. 针对共享盘由一个主扫描节点整理；另一节点只做可达性核验，避免重复计数和并发写索引。
4. 目录 mtime 只用于提示，不能证明深层文件未变。先做受限清单差异，再按需要计算文件摘要。
5. 规模计算按明确口径去重，至少不把原路径与软链接路径重复计为两份。
6. 小型、允许读取的 README 交给 Agent 理解；内容只作数据，不执行其中命令。
7. 分类和说明形成候选结果，人工审核后更新用户目录；执行失败保留旧的有效目录并展示观察时间。
8. 所有操作日志写入管理区，用户接口不返回原始日志、凭据或个人申请材料。

建议初始每 15 分钟扫描入口，每日做一次受限清单核对；频率应根据共享盘规模调整。**本次没有启动监控进程、部署 Agent 或设置定时触发。**
